# PC 桌面歌词拖不到屏幕顶部（issue #23）

日期：2026-11-09
分支：`fix/desktop-lyrics-top-position`（自 main）
来源：https://github.com/bamboostrip/shiyin-music/issues/23

## 背景与问题

用户反馈：「下面可以拖到任务栏附近，可是想拖到顶部的时候，会弹下来不少，
无法固定在屏幕顶部。」

悬浮窗（`desktop_multi_window` 子窗，780 × **408** 逻辑像素）的垂直结构：

```
y=0    ┌──────────────┐  常驻菜单带 212px（透明、穿透；快捷设置菜单浮在此）
y=212  ├──────────────┤  卡片伸缩预留 72px（字号大时卡片向上长）
y=284  ├──────────────┤  工具栏带 36px（hover 出现：播控/锁定/设置/关闭）
y=320  ├──────────────┤
       │              │  歌词带 88px（可见的歌词在这里）
y=408  └──────────────┘  窗口底边 = 卡片底边（位置记忆锚点）
```

**可见的歌词卡片贴在窗口底边**，窗口上方近 300px 是透明死区。拖动用
`window_manager` 的 `DragToMoveArea` → 原生
`SendMessage(hwnd, WM_SYSCOMMAND, SC_MOVE | HTCAPTION)`，而 Windows 的交互式
移动循环会把窗口**顶边**钳在显示器顶边（WPF `DragMove` 同款，见
[SO:3191050](https://stackoverflow.com/questions/3191050/how-to-move-wpf-window-above-top-of-screen)），
其余三边不钳（可拖出屏外被裁切）。两个直接后果：

1. 窗口顶边最多到 0，卡片带顶边最多到 `0 + 408 - 124 = 284`，**歌词永远摸不到
   屏幕顶部**——与用户描述完全一致（"拖到顶部会弹下来不少"）。
2. 存量位置迁移出来的贴顶坐标本来就是负的窗口顶边（底边 88 → 顶边 -320），
   程序化 `setPosition` 放得下，但用户下一次用鼠标拖动时，原生循环第一帧就把
   窗口拽回 `y=0`——"弹下来不少"的另一种触发路径。

## 目标

- 歌词卡片可以拖到屏幕顶边（卡片带顶边 ≥ 视口顶边），并在重启后保持。
- 任何拖动落点都不会让用户"把窗口拖丢"（卡片带至少保留抓取区域）。
- 贴顶后**快捷设置菜单仍可用**：贴顶时窗口顶部的菜单带整体在屏外，点齿轮
  等于没反应，必须处理。
- 现有行为零回归：默认落点、位置记忆/语义迁移、任务栏避让、多屏跨屏拖动、
  未锁定态 hover/穿透轮询、锁定态全穿透。

非目标：横向居中/对齐（issue #16 已在设置里解决）、跟随窗口位置动态改变菜单
方向（现菜单常驻菜单带，不做弹层化改造）。

## 方案

### 1. 拖动改为 Flutter 侧驱动（`lyrics_overlay_window.dart`）

`DragToMoveArea` → `GestureDetector(onPanStart/Update/End)`（`MouseRegion`
用 `SystemMouseCursors.move` 给拖动手感）：

- **按光标绝对屏幕坐标驱动，不用指针 delta**：起手记录
  「光标屏幕坐标 − 窗口顶边坐标」的固定偏移，之后每帧
  `落点 = 光标 − 偏移` → 钳制 → `setPosition`。
  **坑**：Flutter 指针坐标是**客户区**坐标，窗口跟着指针移动后，下一帧
  `DragUpdateDetails.delta` 已经把窗口自身位移扣掉，用 delta 累加会变成
  "追不上指针 / 半速 / 抖动"（window_manager#513 同款复现，作者最后改回
  原生拖动）。绝对坐标与窗口是否在动无关，天然免疫。
- 抓取偏移直接取 `DragStartDetails.globalPosition`（按下瞬间光标相对窗口
  左上角的偏移，无边框窗的客户区坐标即窗口坐标）+ 待还原的菜单让位量——
  按下到首个移动之间窗口若被菜单收起还原了 nudge，同一光标的相对偏移正好
  +nudge，一并折进去，因此"点住哪里就从哪里拖"，首个移动不会丢。
- **按下 ≠ 拖动**：卡片上只有 pan 识别器，单成员手势竞技场在按下瞬间就判胜
  （`GestureArenaManager.close` → `_resolveByDefault`），`onPanStart` 会在
  单击时就触发。这里把"按下"（只预备）与"已移动"（窗口跟随）分开：单点
  歌词不改窗口、不落盘；按下即收起快捷菜单（按在卡片上属于点别处）。
- 被钳制时把抓取偏移锚回实际落点，反向拖动立即跟手（不会先抵消越界那段）。
- 落点计算合并同一帧内的多次 pointer move（一次只跑一轮，期间到的合并到
  下一拍），避免把平台通道灌满；拖动期间指针始终停在卡片带内（窗口
  1:1 跟随指针），加上 Flutter 左键按下时 `SetCapture`（3.44.8
  `flutter_window.cc#L660-667`），不会因移出客户区丢事件。
- 混合缩放多屏：窗口 DPR 一变（拖到另一块缩放不同的屏），抓取偏移按物理
  抓取点不变、逻辑偏移按 DPR 反比重锚（否则抓取偏移 390px 从 100% 跨到
  150% 会跳约 195px）。
- 拖动期间冻结光标轮询的穿透切换：窗口正跟着指针跑，半路把整窗切成
  `WS_EX_TRANSPARENT` 会立刻丢指针事件、卡片 hover 闪断；拖动结束补一拍校准。
- 失焦兜底（`WindowListener.onWindowBlur` → 结束拖动）+ 允许新一轮拖动
  重启：覆盖"拖动中 Alt+Tab 丢鼠标捕获、onPanEnd 不来"导致轮询永久冻结。
- 拖动结束立即落盘（原有的 `onWindowMoved` 是原生 `WM_EXITSIZEMOVE` 才触发，
  自定义拖动不产生该事件；保留原监听作为兜底，降级路径仍在用）。
- 拖动/菜单让位对窗口位置是两路写入，拖动起手先等在途的菜单让位动作落地，
  否则会从"让位后的临时位置"起算。

**降级**：主窗拿不到显示器信息时（`visibleAreas` 为空，screen_retriever 异常），
仍用原生 `DragToMoveArea`。没有屏边界就无法钳制落点，宁可不修贴顶也不让窗口
能被拖出屏幕后找不回来（锁定态全穿透，没有入口找回）。

### 2. 落点钳制（`WindowsDesktopLyricsBridge.clampOverlayDragOrigin`）

纯函数，底边左角语义：

- 纵向有效性按**可见区上下沿合并后的覆盖**判定：卡片带完整落在"某一段并集"
  里就放行；否则底边钳到 `[区域顶 + 卡片带高, 区域底]`。即"卡片带完整可见"
  是下限（贴顶时底边 = 124，窗口顶边 = -284，工具栏带仍可点），上限是工作区
  底边（任务栏上沿，Windows 的 `visibleSize` 已扣掉任务栏）。
  **为什么用并集**：上下排列的多屏若按"卡片中心落在哪块屏"硬切，允许区间会
  在跨界瞬间整体跳变（下屏允许底边 ≥124、上屏允许 ≤-80，可弹几十到上百 px）；
  合并后上下屏各贡献一段，跨界连续。
- 横向：卡片带与任一可见区仍有 80px 重叠就放行（允许跨屏拖动，不在屏边界
  被弹住）；只有完全离屏时才把整卡钳回最近的可见区（防拖丢）。
- 未完全罩住时按"卡片带中心最近"的可见区取上下沿；中心落在屏间缝隙时取
  最近可见区。

### 3. 恢复位置按卡片带感知（`clampOverlayOriginToVisibleAreas`）

`loadStoredOverlayOrigin` 增加可选 `cardBandHeight`：恢复时"可见"判定改为
**卡片带纵向完整 + 横向 80px**，下限改为 `区域顶 + 卡片带高`。
不传时保留历史"整窗 80px 可见"语义（旧测试/降级路径不变）。

- 贴顶活坐标（底边 124）零改动 → 重启不回落，修复"无法固定"。
- 存量迁移出来的底边 88（卡片被屏切掉 36px、工具栏点不到）会被回抬到 124。
- 字号调大后卡片变高，下次启动也不会把歌词/工具栏切在屏幕上方之外。

### 4. 可见区下发（主窗 → 子窗）

子引擎只补注册了 `window_manager`，没有 `screen_retriever`，自己拿不到屏边界。
主窗 `_initialFrame` 已经把显示器可见区算出来了，这里：

- `_initialFrame` 把 `visibleAreas` 缓存到桥接层字段；
- `createWindow` 参数新增 `visibleAreas: [[left, top, width, height], ...]`
  （`encodeVisibleAreas` / 子窗 `decodeVisibleAreas`，畸形载荷跳过不抛）；
- 子窗入口解析后放进 `_OverlayModel`，只在会话内有效（显示器热插拔后重开
  窗口即刷新）。

### 5. 贴顶时展开快捷菜单的临时让位

菜单面板高 212、底边距卡片顶 4，即卡片顶边在屏幕上沿下方不足 216px 时，
菜单带整体/部分在屏外。展开前算下移量
（`menuNudgeForMenuVisibility` = `区域顶 + 212 + 4 - 卡片顶边`，≤0 不动），
把窗口临时下移让菜单完整可见；菜单收起（点空白/失焦/在歌词卡片上按下）或未锁定子树销毁时原路移回。

- 常规位置（屏幕中部/底部）下移量为 0 → **零几何调用**，不破坏"菜单收展不
  触碰原生窗口几何"的既有回归约束（DWM 拉伸闪帧）。
- 落盘位置要扣掉这笔临时位移（模块级 `_overlayMenuNudge`，
  `persistOverlayWindowPosition` 里减掉）：用户记忆的是"菜单收起时的歌词
  位置"，否则每次展开菜单后关窗，下次启动歌词就矮 216px。
- 展开/收起用代次号 + 串行队列：快速连点齿轮时不会交错执行（否则窗口可能
  被移错方向、菜单展开在屏外）；拖动起手会作废在途动作。
- 托盘/设置页切"锁定"会用 `LockedLyricsBody` 整棵替换未锁定子树：`dispose`
  里先把临时位移还原再交棒，否则锁定态歌词凭空矮 216px，且下一次落盘会把
  临时位置写进 prefs，贴顶设置被永久改掉。

## 测试

`test/ui/desktop/desktop_lyrics_test.dart`（+27 条，81 → 108）：

1. `clampOverlayDragOrigin`：屏内原样；**贴顶（窗口顶边 -284、卡片带顶边 0）**；
   越过顶边被钳住；下沿贴工作区底边；水平 80px；跨屏放行；上下多屏（负坐标
   可见区 + 跨界连续不弹跳）；无显示器信息原样返回。
2. `menuNudgeForMenuVisibility`：贴顶 → 216；差多少补多少；空间充足 → 0；
   无显示器信息 → 0。
3. 可见区载荷 encode/decode 往返 + 畸形载荷跳过（缺字段/非数字/宽高非正）。
4. `clampOverlayOriginToVisibleAreas` 卡片带感知：底边 88 → 回抬 124；
   贴顶活坐标零改动。
5. Widget 级：无可见区退回 `DragToMoveArea`；**往上拖 → `setPosition` 收到
   负 y 且卡片带顶边恰好落屏顶**；屏内 1:1 跟手；贴顶展开菜单下移 216 /
   收起移回；空间充足时零几何调用；贴顶展开菜单时单击卡片（不落盘）/
   拖动卡片（先还原再起算）；贴顶展开菜单时切锁定 → 先还原位置再销毁子树。
6. `persistOverlayWindowPosition` 扣掉菜单临时位移。

## 风险与已知限制

- **绝对坐标驱动而非 delta**：这是本方案的关键；用 `DragUpdateDetails.delta`
  会被窗口自身移动污染（见方案 1）。拖动落点为每帧一次
  `getCursorScreenPoint` + `setPosition`，若实测在 165Hz 高刷下有拖影，可再
  降频（例如每 8ms 一拍）。
- **焦点/置顶副作用**：`window_manager.setPosition` 底层是
  `SetWindowPos(hwnd, HWND_TOP, …)` 且不带 `SWP_NOACTIVATE`；窗口本身是
  WS_EX_TOPMOST，拖动中又已经是活动窗，实测应无感。若出现抢焦点/压 IME，
  再在本地 fork 补一行 `SWP_NOZORDER | SWP_NOACTIVATE`。
- **显示器热插拔**：`visibleAreas` 只在建窗时下发，会话中拔插显示器需重开
  歌词窗口才刷新钳制边界（主窗侧的恢复钳制仍按最新显示器信息执行）。
- **贴顶后改字号/单双行**：卡片在窗口内向上长高，可能超出屏幕上沿（工具栏带
  被切）；恢复位置时会按新卡片高度回钳（下次启动生效），会话内可再拖动一次
  校准。属已知限制，未做"设置变化即重钳"。
- **贴顶且工具栏带在屏外**：不允许——钳制下限保证卡片带（含 36px 工具栏带）
  完整可见，因此歌词文字与屏幕顶之间会保留卡片自带的 36px 工具栏带空隙；
  这是"贴顶后仍能点到关闭/锁定/设置"的取舍（与 v3.0.10 及之前贴顶观感一致）。
- **菜单让位的位移**：贴顶状态下展开菜单会把窗口临时下移 216px（歌词随之下移），
  收起后弹回；这是当前"菜单常驻窗口内"架构下唯一能让菜单在贴顶时可见的做法。
- **丢失鼠标捕获**：拖动中 Alt+Tab 等极端操作可能丢 pointer up；已用失焦结束
  + 新一轮拖动重启兜底，但 Flutter 3.44 Windows embedder 本身没有
  `WM_CAPTURECHANGED` 处理（上游 flutter/flutter#189583），无法完全消除。
- 拖动落点/菜单让位依赖 `screen_retriever` 的可见区数据；拿不到时整条自定义
  拖动路径降级为原生拖动（问题回到旧行为，不会更糟）。
