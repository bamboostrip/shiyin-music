## 2. 逐条判定

### 2.1 【需要同步】音频打断 / 蓝牙断开（`56d0c9f` + `9426621` + `574307e` + `c7ba1e6`）

**我们的现状**：`lib/controllers/player_controller.desktop.dart:9-47`

```dart
// 打断结束：若开启了"自动恢复"或"阻止打断"，恢复播放。
if ((autoResumeAfterInterruption || (!audioInterruptionEnabled)) &&
    currentSong != null) { /* 500ms 后 play */ }

// becomingNoisy：只是"可能恢复播放"，没有暂停
if (!audioInterruptionEnabled) return;
if (autoResumeAfterInterruption && currentSong != null) { /* 500ms 后 play */ }
```

三个缺陷：

| # | 缺陷 | 证据 | 上游修法 |
| --- | --- | --- | --- |
| A | **断连不暂停 → 外放**。耳机拔出 / 车机蓝牙掉线时什么都不做，音频由系统改路由到扬声器继续放 | `player_controller.desktop.dart:34-47`（无 `pause`，只可能 `play`） | 新增 `autoPauseOnDeviceDisconnect`（默认 **true**），`becomingNoisy` 立即 `pause()` 并置 `_resumeBlockedByDisconnect` |
| B | **打断结束误恢复**。判据是「有当前歌 + 当前没在播」，没有记录「打断前是否在播」 | `:21-33`（缺 `_wasPlayingAtInterruption`） | 打断开始记录 `_wasPlayingAtInterruption`，结束仅在它为真时恢复 |
| C | **在途请求会绕过暂停**。用户点播后地址还在解析（弱网 2~8s），此时断连/来电已经暂停，解析完成仍会起播 | `player_controller.dart:975` `_requestPlayback()` 无意图守卫；`playSong` 只校验 `_playRequestSerial`，断连不改它 | `_playbackIntentSerial` / `_pendingPlaybackIntent` + `_startPlayback(expectedIntent:)`；意图在**公开入口**登记，加载完成不得授予新权限 |

另有两点是上游这轮的连带改动，我们同步时要一起做：

- **`AudioPlayer(handleInterruptions: false)`**（`9426621` 改 `music_audio_handler.dart`）。
  我们 `music_audio_handler.dart:137` 是裸 `AudioPlayer()`，just_audio 自己也会在焦点回来后
  起播，与 B 叠加。改由控制器独占后，**duck 的音量衰减也要自己接管**
  （`_volumeBeforeDuck` / `_duckedVolume` 一对字段）。
- **`play({bool userInitiated = true})` / `pause({bool userInitiated = true})`** 与
  `attachTransportControls(onPause:, onPlay:)`。我们 `music_audio_handler.dart:1128/1169`
  没有这个参数，`player_controller.dart:262` 也只传了 `onNext/onPrevious`。
  没有它，通知栏/媒体键的「播放」就分不出是用户点的还是流程自动发的。
- **启动自播要降级为「非用户意图」**：`home_page.dart:818-825` 现在直接
  `resumePlayback()` / `playSong(...)`，应带 `userInitiated: false`（`c7ba1e6`）。

> 影响面：**B 默认不可见**（我们 `autoResumeAfterInterruption` 默认 `false`，上游是 `true`），
> 只有用户开了「自动恢复播放」或「阻止打断」才复现；**A 和 C 是无条件的**，A 在 Android 上
> 每次拔耳机都会发生。桌面端 `_setupAudioSessionListeners` 在 Windows 走 catch 分支，
> 同步时不要动 `_ensurePlaying` 那条曲末重播收口（PC 曲末问题是另一套机制，见项目记忆）。

### 2.2 【需要同步】下载元数据（`d688884` 的下载部分）

**我们的现状**：`download_service.dart:604-607` 只在路径以 `.mp3` 结尾时注入 ID3，
注释明写「FLAC 需 Vorbis comment，不在本期范围，直接跳过」；`id3_tag_writer.dart:59-60`
还有一层二次守卫。四个缺口：

| # | 缺口 | 证据 |
| --- | --- | --- |
| A | **FLAC 无任何标签**（歌名/歌手/专辑/封面全丢，第三方播放器与车机只显示文件名） | `download_service.dart:604`、`id3_tag_writer.dart:59` |
| B | **扩展名可能撒谎**：`fileNameFor` 按请求音质定扩展名，而 `_downloadQualityFallbackChain` 会把 flac 降级到 320/128 → 实际 MP3 却叫 `.flac`，第三方播放器按扩展名选解析器必然错 | `download_service.dart:415`、`download_controller.dart:697` |
| C | **反向风险**：`.mp3` 名下其实是 FLAC 时，我们往里写 ID3v2 前缀，破坏 `fLaC` 头 | 同上（按扩展名分派而非按字节） |
| D | **下载不抓歌词**：不写 `.lrc` 旁挂、不内嵌 USLT/Vorbis `LYRICS` | `download_service.dart:602-607` |

D 在**上游**那里价值更高（他们下载完仍需要联网匹配歌词），而在我们这里：`LocalLyricsService`
的加载顺序确实是「同名 `.lrc` → 内嵌 → 缓存 → 在线匹配」，但它**只对 `song.source == local`
生效**（`player_controller.lyrics.dart:61`），下载回来的歌仍是 `kugou` 源，所以边文件
**不会**被我们自己的播放器读到——它只服务第三方播放器/车机/U 盘场景。这点别夸大
（§5.4 已按 review 修正过一次表述）。

上游的解法拆成四个文件，**大部分可以直接搬**：

- `lib/services/audio_file_format.dart`（54 行，纯 dart:io 字节探测，含跳过 ID3v2 头再判
  `fLaC`/MPEG 帧同步）→ **原样可用**。
- `lib/services/flac_tag_writer.dart`（256 行，Vorbis comment + PICTURE 块，保留 STREAMINFO
  在首位、流式复制音频帧）→ **原样可用**，只改 vendor 字符串。
- `lib/services/download_metadata_writer.dart`（185 行）→ **必须裁剪**：上游这里
  `import 'package:audio_metadata_reader'` 读旧标签、并 `http.get` 拉封面（4s 超时）。
  本 fork 明令禁止该依赖（`id3_tag_writer.dart:18-20`、`local_lyrics_service.dart:11-13`），
  封面也统一走 `ImageDiskCache`（`download_service.dart:650-659`）。裁剪后保留：
  格式探测 → 按格式分派 → 歌词文本 → `.lrc` 边文件（原子写 + 临时文件清理）。
- `downloadLyricsText()`（同文件底部，LRC 时间轴 + 翻译）→ 原样可用。

接线改动：

| 文件 | 改动 |
| --- | --- |
| `download_service.dart` | 落盘后 `inspectAudioFile` → 扩展名不符就 rename（并让调用方用新路径）；标签写入改走 `DownloadMetadataWriter`；`cancel()` 同时删 `.lrc` |
| `download_service.dart` `_audioContentLength` | 目前只剥 ID3v2 头（`:694-695`）。FLAC 有了标签后，重下同名歌的「音频字节数」比较要把 Vorbis comment/PICTURE 也剥掉，否则会误判成「同名不同歌」多存一份 |
| `download_controller.dart` | 下载时用 `api.lyrics()` 取歌词；新增 `saveLyricsFile` 开关（默认关，内嵌失败时自动落 `.lrc`）；元数据/封面/歌词抓取加 3 路并发上限（批量下载时不要一次铺开整张歌单） |
| `settings_page.dart`（缓存管理） | 加「同时保存 LRC 歌词」开关，放在「下载文件」项下面 |

### 2.5 【需要同步】播放进度持久化（上游 `c113193` 的一半）

**这项是本次新发现，不在 §1 的 16 提交窗口里**——它是 `2026-11-10` triage 就列出的
「记住退出播放进度」，但一直没落地。

现状：`_savePlaybackState()`（`player_controller.settings.dart:373-392`）只存
`queueBaseIndex / currentSongHash / queue / currentIndex / playbackMode`，**没有播放位置**；
`resumePlayback()`（`player_controller.playback.dart:1453-1455`）恢复时
`playSong(songToPlay, queue: queue)` 不传 `initialPosition` → **永远从 0:00 起**。

用户感知：关掉客户端再打开（或开机自启），歌是同一首，但进度回到开头。
桌面上这条比移动端明显得多（桌面是「随时关随时开」）。

上游解法（`c113193`）：新增 `_resumePosition` + `hasPendingResumePosition`，
持久化时按 `currentSong.hash` 记 `_readSavedPosition`，恢复时回填 `initialPosition`，
且**只在同一首歌**上生效（换歌就作废）。改动集中在快照读写两处，不需要动播放状态机。

## 4. 验证建议

- 断连：Android 真机播歌 → 拔有线耳机 / 关车机蓝牙 → 应立刻静音（不再外放）；
  再点播放能正常起播（`_resumeBlockedByDisconnect` 只应由显式播放解除）。
- 打断：开「自动恢复播放」→ 手动暂停 → 来电挂断 → **不应自动播放**；
  播歌中来电挂断 → 应恢复。
- 在途请求：弱网（或被墙）下点歌 → 地址解析中拔耳机 → 解析完成后**不应起播**。
- 下载：无损下载 → 用第三方播放器（或 `ffprobe`）确认标签与封面；故意选一首无 flac 源的歌
  → 文件名应是 `.mp3` 而不是 `.flac`；下载目录旁应有 `.lrc`（开关打开时）。
- 回归红线：PC 曲末重播（`_ensurePlaying` 的 pause→seek→play 三步）、
  车机左侧面板尺寸、桌面歌词悬浮窗几何——这三块本轮不应有任何改动。

**本来就不 duck**——所以这里保持原行为，既与改造前一致，也不会和 `LoudnessService`

### 5.4 review 后的三处修正（同日）

自查发现并修掉三个隐藏坑：

1. **`_interruptionRequiresPause` 是闩锁，漏发 end 事件会让播放键永久失效。**
   该标记只在打断结束事件里清；部分 ROM / 通话被打断的路径会漏发 end，之后
   `_requestPlayback` 一律拒绝，用户点播放毫无反应、只能重启 App。
   改为在 `_handleManualPlay()`（用户显式播放）里一并清除——显式意图强于系统事件，
   真正仍在通话中时由音频焦点裁决。
2. **两处自动续播被当成了用户意图。** 私人 FM 队列末尾自动续批、VIP 领取成功后的
   重试原来都传默认 `userInitiated: true`，会借机解除「蓝牙断开停止播放」的保护，
   断开后自己续播到扬声器。已改为 `false`。
3. **Android 媒体库扫描发生在写标签之前。** MediaStore 在扫描当刻快照艺人/专辑/封面，
   先扫后写会让系统音乐库与车机蓝牙列表长期显示「未知艺人」。扫描移进
   `DownloadController._enrichDownload()`，在 `writeDownloadMetadata()` 之后。

另修正一处**表述错误**：原文说「`.lrc` 在本 fork 价值更高」，实际 `LocalLyricsService`
只对 `song.source == local` 生效，下载的歌读不到边文件（见 §2.2 的 D 项）。

## 7. 播放进度持久化（已实施，§2.5）

主流桌面播放器都是「记住当前曲目**和位置**」，且多数是**可关的开关**：foobar2000
「Save playback state when closing and resume on next startup」、网易云 PC「程序启动时
记住上一次播放进度」、AIMP 同类；Apple Music / 手机端 QQ/网易云/酷我 默认开启。

### 语义

**全局单点**：只记「最后在播的那一首 + 位置」，下次启动恢复它；不做全库
`hash→ms` 表——本 fork prefs 是整文件重写（PC 约 1.5MB），塞进几百条记录是性能倒退。

### 与上游的差异（按本 fork 架构调整）

| 项 | 上游（`c113193`/`165eb46`） | 本 fork |
| --- | --- | --- |
| 进度归属 | handler 里加 `loadedSong`（`setAudioSource` 成功后才更新） | 控制器里的 `_positionOwnerHash`（`loadSong` 返回且身份校验通过后更新）。**不用改 handler**，34 个测试桩无需加 `loadedSong` |
| 0 覆盖 | 只把 `ms<=0` 当无记录（仍会写 0） | owner 对不上 / 仍在加载或定位时**完全不写**；归属成立后的合法 0（拖回开头、刚起播就暂停）如实写，避免残留上一次的旧位置 |
| 曲末 | 不处理 | 剩余 ≤3s 不恢复（用剩余时长而非百分比，长播客不受影响） |
| 落盘节奏 | 5s 一次（所有平台） | 仅移动端 5s；桌面不建周期定时器（PC prefs 每次写都整文件同步落盘，周期写等于常驻磁盘抖动） |
| 落盘触发点 | 周期 + 暂停 | 移动端周期 + 暂停 + `flushPlaybackState()`；桌面靠暂停 + 退后台/退出钩子，且钩子 **await 进度写** 后再返回（否则 `TerminateProcess` 会丢掉未完成的写） |

### 落点

- `player_controller.dart`：`parseSavedPosition()`（纯函数，含旧格式兼容）、
  `_resumePosition` / `hasPendingResumePosition`、`_positionOwnerHash`、
  `_saveCurrentPosition` / `_startPositionSaving` / `_stopPositionSaving`（基类）。
- `player_controller.settings.dart`：恢复时读位置 → `_isResumablePosition` 过滤 →
  写进内存 position 与待恢复标记。
- `player_controller.playback.dart`：`playSong` 入口消费待恢复值、
  `resumePlayback` 第一首带 `initialPosition`、`togglePlay` 暂停时立刻存一次。
- 不加设置项：恢复位置与「开机自启播放」独立——不开自启时用户点播放也会从这里续
  （`togglePlay` 的 idle 分支本来就用内存 position）。

### 用例（`test/controllers/playback_position_restore_test.dart`，11 条）

`parseSavedPosition` 的 hash 匹配/旧格式/脏数据；同曲恢复 + 待应用标记；他曲不恢复；
尾 3 秒不恢复；`resumePlayback` 真把进度送进引擎（fake handler 记 seek）且只用一次；
播放中 `flushPlaybackState` 写入 `{hash, ms}`；合法的 0 与「加载中被暂停」都能覆盖旧记录；
未起播过时不覆盖磁盘原记录。

## 8. 独立复核轮（2026-11-17 同日晚，同步后全面 review）

与 §5.4/§5.6 的自查不同，本轮是对照上游原始提交（`56d0c9f` / `9426621` / `c7ba1e6` /

### 8.1 核对通过、无需改动的部分

- **意图代次机制 vs 上游 `_startPlayback`**：语义一致（入口登记、加载完成校验、
  finally 只清自己的企图）；我们的版本还多了两点上游没有的收紧——
  `_requestPlayback` 的断连/打断闸门对**不传 `expectedIntent` 的旧入口也生效**，
  以及 `_handleManualPlay` 对漏发 end 的打断闩锁自愈（d099b30）。§8.2 初版在
  私人 FM 入口漏了「加载完成校验」，§8.5 已补齐。
- **becomingNoisy 的上游演进**：`56d0c9f` 初始版只在 `isPlaying` 时暂停且不清恢复
  标记；`9426621` 已改成与 fork 一致（无条件暂停 + `_cancelAutomaticResume` 清
  `_wasPlayingAtInterruption`），杜绝「断连后迟到的打断结束又把声音放回扬声器」。

- **`autoPauseOnDeviceDisconnect` 默认 true** 与上游一致，持久化/设置页/摘要齐全。
- **§2.3/§2.4「不需要同步」判定**逐条以代码核实成立（上文两处引用已按实际情况
  修正：`_updateQueue` 实为 `setSongQueue`；`_desktopLyricsUserDismissed` 声明位置）。
- **FLAC 写入器字节级**：synchsafe 校验、v2.4 footer 位、块类型 127 非法、1024 块
  上限、STREAMINFO 首块校验、Vorbis 小端长度域、PICTURE 布局与 PNG/JPEG 尺寸解析
  （IHDR 偏移、SOF 段扫描含 DHT/DAC 排除）均正确；Dart 中 `&` 优先级高于 `!=`，
  所有位判断按预期结合。音频帧 `addStream` 流式复制，不整读进内存。
- **扩展名纠正与下载索引闭环**：`localPathFor`/`localPathForAnyQuality` 走索引的

  `resolveNonCollidingPath` 按剥标签后的音频字节数比较，同内容覆盖、不同内容退
  `(n)` 名。
- **`_flacMetadataLength`** 的守卫（越界判 0 不剥、读失败退回不剥）方向正确：
  宁可多存一份，不误判成同一首而覆盖。
- **进度持久化**：`_positionOwnerHash` 归属、`isPreparing`/`_pendingInitialPosition`
  双守卫、合法 0 如实写、blocked 分支补落盘、桌面退出钩子 await 进度写、移动端
  5s 周期表 `??=` 不重复创建——均无问题。**但**「`togglePlay` idle 分支用内存
  position，不开自启、手动点播放也能从上次位置续播」这一条**不成立**：冷启动后

### 8.2 发现并修复：`startPersonalFm` 意图登记时机（首轮结论）

上游 `9426621` 对 `startPersonalFm` 的处理是**方法入口**先 `_handleManualPlay()` +
登记企图，拉取完成后 `playSong(userInitiated: false)`。本 fork 的实现一直是拉取
完成后才调 `playSong(默认 userInitiated: true)`——`_handleManualPlay()` 在**拉取
之后**才执行，会把拉取期间（弱网可达数秒）刚建立的断连/打断保护解掉：表现为
「点开私人 FM → 拉取期间拔耳机（已暂停防外放）→ 拉取完成直接从扬声器外放」。
这正是 d099b30 修的三处同类问题（FM 续批/VIP 重试/网络恢复重播）漏掉的第四处入口。

修复（入口与清理对齐上游；拉取完成时的代次校验见 §8.5）：

- `startPersonalFm` 入口先 `_handleManualPlay()` + 登记 `_pendingPlaybackIntent`
  （点按即用户意图，此时解除保护是**正确**语义）；
- 拉取后的 `playSong` 传 `userInitiated: false`（拉取期间建立的保护不得被迟到的
  「用户意图」声明解除）；
- finally 补入口企图的清理（拉取失败/为空时不得残留，否则打断开始的
  「本来就要播」采样会误读）。

新增用例：`audio_interruption_state_test.dart`「私人 FM 启动拉取期间断开：拉取完成
后不得外放起播」（fmGate 门控 + becomingNoisy + 断言不起播、不落错误态、显式播放
仍能解除保护）。

> 8.5 复核补记：本节初版只做到「入口登记 + 拉取后 `userInitiated:false`」，
> **拉取完成后没有校验入口代次**，暂停/打断结束仍会被吞掉；「对齐上游」也只对
> 入口与清理成立。补齐方式与刻意保留的 fork 差异见 §8.5。

### 8.3 核对过、与上游保持一致（不改）的「fetch-then-play」

`rank_page` 播放整榜、`home_page` 播放整歌单、`main.dart` 深链播放都是

断连、拉取完成后以用户意图解除保护」的窗口，但上游自己在这三处也保留默认

### 8.5 复核补记（2026-11-18）：拉取完成后必须校验入口代次

§8.2 的修复只做了「入口登记 + 拉取后 `userInitiated:false`」，**拉取完成后没有
校验入口代次**：`playSong` 在拉取结束后重新取当前 `_playbackIntentSerial`，导致
`_requestPlayback` 的 `expectedIntent` 永远自洽。上游 `9426621`（当前 master 同）
在拉取后是直接放弃整个启动：

```dart
if (requestSerial != _personalFmRequestSerial ||
    intentSerial != _playbackIntentSerial) {
  return false;
}
```

（上游 `lib/controllers/player_controller.dart:927-930`。）

漏掉它的真实问题（fmGate 用例已复现）：「点开 FM → 拉取期间按暂停 → 拉取完成
→ FM 仍然起播」。同类还有：拉取期间来电、通话结束（默认
`autoResumeAfterInterruption=false`，结束分支会 `_cancelAutomaticResume` 推进
代次）→ 上游作废，本 fork 仍会起播。

本 fork 的处理**有意与上游不同**：不放弃整个启动，改为「预载队列 + 拦截起播」，
保留断连后「队列已就绪、按播放即续」的既有体验（§8.2 用例依赖它），也避免被
取消的启动在首页弹「私人 FM 加载失败」。

- `playSong` 增加可选 `int? expectedIntent`：为空时用进入方法时的代次（旧入口
  行为不变）；非空时用调用方更早登记的代次去 `_requestPlayback` 比对。加载照常
  完成（队列/音源就绪），代次对不上只拦起播。
- `startPersonalFm` 把入口代次作为 `expectedIntent` 传给 `playSong`。
- **重试链路同样转发代次**：`playSong` 失败后的 2s 网络自动重试、VIP 领取后的
  重试（含切音质路径）原本都会重新取当前代次，等于给过一次「起播授权」；现均
  沿用入口代次，等待期间用户暂停/断连时重试不会起播。
- **期间已恢复播放时放弃预载**：若拉取期间用户暂停后又按了播放（或原曲重播），
  这是比点按 FM 更晚的意图；此时不再预载 FM（否则会把正在播的音频换掉、表现为
  「最后一次操作是播放却静音」），也不返回错误。
- 新增四条用例：「拉取期间用户暂停：完成后不得起播，队列预载且显式播放可续」；
  「拉取期间暂停后恢复播放：不得顶掉正在播的歌」；「拉取期间打断结束（默认不
  自动恢复）：完成后不得起播」；「自动重试不得绕过过期的企图代次」（首次解析
  失败进入 2s 重试，重试解析成功后仍不得起播）。

已知边界（本次不动）：入口 `_handleManualPlay()` 在拉取前就解除断连保护，拉取
失败时不回滚（上游同样如此）。理论上「拔耳机 → 点 FM → 拉取失败 → 网络恢复」
会让网络恢复重播把旧歌放回扬声器；概率低，先记录，不为此扩状态机。

文档修正：§8.1 的 becomingNoisy 对比对象应为 `56d0c9f`；代码注释也不再写「来电
打断会推进企图代次」——打断 begin 只设闩锁，推进发生在断连和打断结束的 cancel
分支。

### 8.6 合并后全量复核（2026-11-18）：4 处修复 + 2 处收紧

对 `v3.0.20..main` 全部提交做合并后复核，发现并修复：

1. **自动跳过不得解除断连/打断保护**（确认漏洞，已补用例）：`next()` 被当作
   用户显式切歌调用 `_handleManualPlay()`，而失败自动跳过复用了 `next()`；
   保护期间任何自动播放请求失败都会把保护解掉、下一首外放。拆出
   `_advanceToNext()`（纯队列推进，不登记用户意图），自动跳过改走它。
2. **重试必须沿用本次起播的代次**：`playSong` 的 2s 自动重试与 VIP 领取重试
   原先把 `expectedIntent` 参数继续下传；普通入口该参数为 null，内层会重新
   捕获新代次，等待期间暂停/打断结束不会作废重试。改传本次的 `intentSerial`。
3. **`/song/url` 响应分类**：业务错误信封/空响应不再被当成「空地址」（否则
   会被 `NoPlayableSourceException` 一次即跳，限流/会话失效时可连跳）；统一
   转 `ApiException` 走可重试失败，仅服务端明确返回空地址才判无音源。
4. **切音质 blocked 分支落盘**：`isPreparing` 仍为 true 导致
   `_saveCurrentPosition()` 空操作；增加 `allowWhilePreparing` 显式豁免。

两处收紧：无音源连跳上限后置 `_tailSkipExhausted`（网络恢复不再重试并重复
提示）；`parseSavedPosition` 在目标歌 hash 为空时拒绝任何记录（无法归属）。

验证：`flutter analyze` 无问题；全量 **2004 passed / 1 skipped**（较 §8.4 +8；
1/2/4 均验证过「回退实现则对应用例失败」）。

仍记录、不在本轮修的边界：旧下载不迁移/不补扫（收益只覆盖新下载）；标签
写入仅在自定义公共目录对媒体库有实际意义；ID3 要求 `.mp3` 后缀与按字节分派

### 8.9 手机冷启动续播缺口（2026-11-24，issue #38 排查）

用户 issue #38 反馈「重进 App 播放位置丢失」，同时反馈车机能续上、手机不能。定位到两条
独立缺口，都在「引擎还没装载音源（idle）」这个窗口里，车机因为开机自播走另一条路径
（`resumePlayback` 直接用 `_resumePosition` 当 `initialPosition`）而没有暴露：

1. **内存 position 被空载回调抹成 0**：恢复时 `_setPositionBase(saved)` 只写内存，
   而 `positionStream`/`playerStateStream` 监听无条件 `_setPositionBase(audioPlayer.position)`；
   冷启动引擎 idle、position 恒 0，音频服务绑定 / 通知栏媒体键 / 前台服务重建任一次
   上报都会把 90s 冲成 0。`togglePlay` 的 idle 分支读的就是内存 position，于是手机
   手动点播放从 0 起播（§8.1 那条判断因此不成立）。
   修法：新增 `_shouldAdoptEnginePosition()`——还有待恢复进度（`_resumePosition != null`）
   且引擎 idle 时不采信引擎上报；`togglePlay` idle 分支改为
   `_pendingIdlePosition ?? _resumePosition ?? position`（与上游 `_prepareRestoredSong`
   的 `restoredPosition = _resumePosition ?? position` 同义）。
2. **stop 后用 0 抹掉磁盘进度**：用户 stop / 前台服务被回收后引擎 idle，而
   `_positionOwnerHash` 仍在，`_saveCurrentPosition` 会把 `{hash, ms:0}` 写盘，
   下次启动 `parseSavedPosition` 因 `ms<=0` 判为无记录。
   修法：`ms == 0 && processingState == idle` 不写盘——与上游 `resolvePositionRecord`
   「音源未加载 → 不改写磁盘」对齐（本 fork 用归属标记替代 `loadedSongHash`，
   此处补上「音源已释放」这一半）。

**产品口径**：默认仍不自动播（`autoPlayOnStartupEnabled = false`），重进 App 由用户
点播放键续；设置里打开「启动时自动播放」则走 `resumePlayback` 自动从断点起。

**`hasPendingResumePosition`**：上游 `c113193` 引入后同样只有定义、没有 UI 调用方
（`git grep` 上游全仓仅 1 处命中）。它描述的是「恢复进度还没交给引擎」的内部时刻，
保留给回归用例观测与将来「上次听到 xx:xx」提示，不接 UI、不删除。

验证：`flutter analyze` 无问题；全量 **2237 passed / 2 skipped**；新增 3 条用例
（空载回调不冲位置、手动播放从恢复位置续、stop 后 flush 不写 0），前两条在回退
实现时分别验证为失败。
